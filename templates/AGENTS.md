# AGENTS.md — AI 协作操作契约（ai-coding-kit 模板）

本文件是所有 AI 助手进入本仓库的**第一份必读契约**：规定文档放哪、技能链怎么走、何时必须校验。换工具/换 IDE，规则不丢失。

> 模板使用说明：安装器（`ai-coding-kit/adapters/install.ps1 -WithTemplates`）仅在目标项目缺失 AGENTS.md 时生成本文件；已存在则跳过不覆盖。带「项目专属」标记的节请按项目实际填写，其余为 kit 通用纪律。

## 文档体系（OpenSpec 式三区）

- `docs/INDEX.md`   = **唯一入口**，会话开始先读此处。
- `docs/specs/`     = **当前真相**。编码前必读对应域 `spec.md`；未在其中定义的行为视为未定义，禁止臆测。
- `docs/changes/`   = **进行中变更**。一个变更一个文件夹，四类产物按 `proposal → specs(delta)+design → tasks → implementation` 递进。
- `docs/archive/`   = **已结案**。只读，不得作为当前行为依据。
- `docs/reference/` = 外部/上游只读资料；`docs/manual/` = 面向使用者手册。

## 构建与验证命令（全链路统一口径）

- 每阶段做真实验证（编译/测试）后才可声称完成；构建、测试、回归的具体命令以当前栈 rules 的命令口径为准（如 java-backend、python-backend）。
- 前端内联脚本：node `vm.Script` 语法校验（提取脚本须 UTF-8 无 BOM 写盘，PowerShell 默认 ANSI 读中文会误报）。
- 命令输出捕获：PowerShell 下把含中文的命令输出（git/mvn/python 等）捕获进变量做比对或解析前，必须先置 `[Console]::OutputEncoding=UTF8`，否则 PS 5.1 按 ANSI 解码产生乱码假阳性；直接显示不受影响。
- PowerShell 脚本编码：含中文的 `.ps1` 必须 UTF-8 **带 BOM**（无 BOM 时 PS 5.1 按 ANSI 解析，中文乱码引发 ParserError）；与上条「前端内联脚本须无 BOM」方向相反，不得混淆。部分编辑工具保存时会剥掉 BOM，编辑 ps1 后必须重新加 BOM 再用 `[System.Management.Automation.Language.Parser]::ParseFile` 验证零错误才算完成。
- 内联插值规避：经外层 PowerShell 调 `powershell -Command "..."` 时，双引号内的 `$var`/`$_` 会被外层 shell 先行插值（吞成空值或错值）；含变量的命令一律写临时 ps1 文件执行（临时脚本只放项目忽略区），或改用不含 `$` 的参数形式（如 `Get-ChildItem -Name`）。
- 测试全绿才可回写 `tasks.md` 勾选；既有红测如实登记归属，不夹带修复。

## 技能链

```
/spec propose → /product-senior(可选) → /grill-me → /requirement-design
              → [/architecture-design(有架构决策时)]
              → /ui-dev(前端) ↔ /senior-dev(后端) 或 /tdd(TDD)
              → /code-review(质量门禁) → /spec verify → /spec archive
```

各技能产物的**落盘路径由 `/spec` 契约统一规定**，不再人工命名、不在文件名内嵌日期。无 Skill 自动调用机制的 IDE，按上述顺序手动逐个输入斜杠命令，链式语义不变。

## 铁律

1. 禁止在 `specs/` 写内部类名、DDL、框架选型（`代码证据` 行=类#方法粒度除外）；实现细节进 `design.md`。
2. 每条 `SP` 须以代码/配置为准核验并标注证据；核不动的进该域 `## 待核验` 节，禁止当作已确认规则；`待核验` 条目不得被 delta 引用为「修改规则」。
3. 禁止在变更目录塞一次性快照文档 → 归 `archive/`。
4. 禁止在特性变更里夹带无关重构（以 `proposal.md` 的 `What Changes` / `Non-goals` 为准，`/code-review` 做越界拦截）。
5. 归档前必须 `/spec verify` 通过；`tasks.md` 状态一律用标准 markdown 任务清单（`- [x]` 完成 / `- [ ]` 未完成），有未勾选项不得"警告着归档"，必须逐项写明处置。
6. 文件名禁止内嵌日期做版本，版本交给 git；搬迁一律 `git mv` 保历史。
7. **执行期不打断**：一旦方案/计划已被用户明确确认（或用户下达的是直接执行指令），多任务链路 SHALL 按既定顺序连续推进，每阶段做真实验证（编译/测试/回归）后直接进入下一项；禁止中途停下来等待用户点"继续"。
8. **提问/咨询先给方案**：用户以提问、咨询、评审、故障排查口吻发起（非明确执行指令）时，SHALL 先输出【方案 + 具体改动清单（文件路径 · diff 预览 · 影响面 · 待裁决点）】供用户 review，仅在用户回复"开始/执行/同意/按 X 方案做"等授权指令后才动手编辑文件。斜杠命令（`/spec`、`/grill-me`、`/code-review` 等）与已在第 7 条覆盖的执行中任务流，不受第 8 条约束。
   边界判定：
   - 提问/咨询类信号词：为什么、怎么办、能不能、应该如何、评审、分析、看看、帮我判断、这是什么原因……
   - 执行指令类信号词：开始、执行、同意、按此做、改一下、实现、动手、去做、继续……
   - 语义模糊时，以"用户是否已明确授权动手改文件"为准；未授权一律先方案。

## Credits 节约约定

1. **模式分级**：只读咨询（问原因/评审/看日志）用只读模式；明确改代码才用执行模式；小改动禁用多代理编排。
2. **探索预算制**：只读取与本次修改直接相关的文件（目标文件+直接依赖），禁止无目标全仓遍历；信息不足先向用户要指定文件/字段，不自行翻项目猜。
3. **最小改动**：编辑走文件工具只改必要片段，对话不整文件全量复制；禁止"顺便"追加需求外的优化/校验/异常包装。
4. **输出精简**：不科普基础概念、不逐行翻译日志、不复述已知背景；解释性文字最短，优先结论+关键改动点。落盘产物（代码/注释/docs/commit message）不受精简约束，一律完整正常语句。
5. **会话策略**：同一任务在同一会话继续；任务切换/话题跑偏坚决新开会话，不跨任务复用长上下文。长任务跨会话时，会话结束前须把交接三件套（已完成/进行中/下一步 + 验证证据）回写 `docs/changes/<名>/tasks.md` 备注或 `implementation.md`；新会话按 INDEX → changes 产物接管；无变更目录时按 IDE 记忆机制（若有）落任务摘要。
6. **大文件本地先行**：日志/Excel/PDF/Word 一律先本地提取结构化摘要，只把摘要交给 AI 归因，禁止整文件/整目录进上下文。
   - 日志：用项目现成分析脚本聚合，去重计数，只喂 top-N 错误+堆栈；
   - Excel：临时 Python 脚本（openpyxl/pandas）先出 sheet 清单+表头+行数+抽样+异常统计，明细按需筛选目标行；
   - PDF/Word：临时脚本（pypdf/python-docx，缺库按需安装）先提大纲/标题，按关键词定位只读目标页/段；提取结果落盘缓存，续聊不重复解析。
7. **技能链裁剪**：按变更大小裁剪技能链；`/code-review` 只在核心逻辑变更/合并前跑一次；不满意先改 prompt，不反复 regenerate（每次都是新计费请求）。
8. **全仓评审地图先行**：review 整个项目前先用脚本生成仓库地图（目录+行数+模块清单）与静态指标（编译、CRAP 等），AI 按地图选重点；优先评审 git diff，全量评审按模块分批、结论落盘 `code-review/`，跨会话只读报告不重读源码。

## 编号体系

`SP-xx`（specs 原子规则，跨变更长期唯一，缩写登记于 `docs/specs/_domains.md`）
`R-xx`（澄清）→ `FP-xx`（功能点）→ `T-xx`（任务）；三者须可互相追溯，`/spec verify` 校验覆盖完整性。
