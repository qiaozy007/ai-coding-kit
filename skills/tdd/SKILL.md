# tdd 测试驱动开发（AI Coding 阶段）

**MISSION**：启用后所有编码任务（功能实现、Bug 修复、重构）强制 TDD：**先写失败测试（Red）→ 最小实现通过（Green）→ 重构消除坏味道（Refactor）**。禁止先写实现再补测试、禁止跳过重构、禁止无断言的"装饰性测试"。产出达到可编译运行、测试全绿、无坏味道、可迭代维护的生产级标准。

## 技能链定位

- **上游输入**：优先读 `docs/changes/<变更名>/specs/<域>/spec.md` 的 `SP-xx` + WHEN/THEN 行为契约作为测试用例首要来源（每条 SP 的每个 WHEN/THEN 场景至少对应一个测试）；辅以 tasks.md（T 号）、design.md 实施约束、clarification.md 边界共识。
- **与 `/senior-dev` 的关系**：本 Skill 是编码阶段的 TDD 强化模式，两者可叠加——`/senior-dev` 管"代码怎么写对"，本 Skill 管"开发节奏怎么控"。
- **启用场景**：① 用户显式要求 TDD；② 核心业务逻辑（金额/状态流转/数据转换/并发编排）需测试保护网；③ Bug 修复需回归锁定；④ 重构前需特征测试保护。
- **产出契约**：失败测试 → 最小实现 → 重构后干净代码 + 全绿测试，每轮循环交付可验证增量。

## TDD 核心铁律（永久生效）

- **测试先行**：写任何业务代码前必须先有描述该行为的失败测试——铁律不是建议。
- **最小步长**：每轮 Red-Green 只推进一个行为点（一个方法的一个分支/边界），禁止一次写多个测试再批量实现。
- **最小实现**：Green 只写让当前失败测试通过的最小代码（可从硬编码返回值起步），禁止提前实现"将来可能用到"的逻辑（YAGNI）。
- **重构不增行为**：Refactor 只消除重复/简化条件/提取方法/改善命名；新增行为必须回 Red 先写测试。
- **测试即文档**：命名与结构一眼看懂"测了什么、什么条件下、期望什么结果"。
- **零装饰测试**：禁无断言、禁只测 happy path、禁断言无关字段凑覆盖率。
- **失败即信号**：测试失败先判断是"实现错了/测试写错了/对行为理解有误"，理解有误回上游需求确认，不急着改测试。
- **编译通过优先**：每轮循环结束代码必须可编译、测试可运行；版本对齐项目实际测试框架（测试框架与断言库以当前栈 testing-* rules 为准），复用既有测试基类，不重复造轮子。

## Red-Green-Refactor 循环

### Red：用测试精确描述下一个行为
1. 从上游 T/FP 验收标准提取一个行为点：输入什么、什么条件下、期望什么输出/副作用。
2. 命名 `方法名_场景_期望结果`；Given-When-Then 三段式；断言与 Mock 写法以当前栈 testing-* rules 为准。中立伪代码示例（具体语法按当前栈翻译）：
   ```text
   test 计算房价_普通日_返回基础价():
       // Given — 准备测试数据与前置条件
       config = 构造房价配置(基础价 = 388.00)

       // When — 执行被测行为
       result = 房价服务.计算房价(config, 日期 = 2026-09-22)

       // Then — 断言期望结果
       断言(result == 388.00)
   ```
3. 运行确认**编译失败或断言失败**（Red）。意外通过 = 理解有误或测试写错，停下来重新审视，不直接写实现。
4. 失败消息必须能区分本测试与其他测试的行为，禁止多个测试因同一原因失败却看不出差异。

### Green：最少代码让测试通过
1. 只写让测试通过的代码，逐步泛化，不一步到位写"完整方案"。
2. 最小实现不等于烂代码——当前栈后端 rules 硬约束（空值防御/异常/命名/日志）同样生效。
3. 运行确认变绿；失败就调试修复，不跳过。
4. 当前测试不需要的分支就不写 if/else，不需要的持久化就不写数据库操作。

### Refactor：测试保护网下改善结构
1. 先确认全绿作为重构起点。
2. 消除坏味道：重复→提取方法/工具类；过长→拆私有方法；深嵌套→guard clause；魔术数字→常量/枚举；过大类→按职责拆；命名→揭示意图。
3. 每做一次重构立即跑测试；测试代码遵循与业务代码相同规范，重复与命名同样打磨。

## 按场景工作法

- **新功能**：读上游输入 → 列测试用例清单（happy path/边界/异常）请用户确认优先级与覆盖范围 → 逐用例循环（每轮一个）→ 全量回归确认无回归 → 按交付格式输出。
- **Bug 修复**：先写复现测试确认 Red（证明 Bug 存在且测试能捕获）→ 改根因不改症状使其 Green → 全量回归 → 横向排查同类缺陷模式，必要时补测。
- **安全重构**：无测试先写特征测试（characterization test，只测"实际"行为不看"应该"）锁定现状 → 小步重构频繁验证 → 交付列重构手法、改名映射、调用方影响清单。
- **遗留代码补测**：先读代码理解行为不急改 → 对关键公开方法写特征测试锁定现状（含看似不合理的行为）→ 有保护后按安全重构推进 → 按业务重要性排序补测，不为覆盖率凑数。

## 测试设计基线（rules 自动注入，不在本技能复述）

- 测试硬约束（结构与命名/Mock 隔离/断言/分层/覆盖策略与边界检查清单）：core `testing.md` + 当前栈 testing-* rules。
- 本技能只管 TDD 节奏（Red-Green-Refactor）与按场景工作法；rules 与本技能冲突时以 rules 为准。

## 交付输出格式

每次交付按此结构输出。**交付完成后固定落盘**：写入 `docs/changes/<变更名>/implementation.md`，并**回写 `docs/changes/<变更名>/tasks.md`**：对应 T 项勾选 `[x]` 并附**完成证据**（测试类/方法名或命令与结果）；未通过全量测试不得回写勾选。

```markdown
## 功能概述
[1-3 句，标注对应 T 号/FP 号]

## TDD 循环记录
| 轮次 | 阶段 | 测试用例 | 结果 | 说明 |
|------|------|----------|------|------|
| 1 | Red | `method_scenario_expected` | ❌ 编译失败 | 新增测试，描述XX行为 |
| 1 | Green | 同上 | ✅ 通过 | 实现最小逻辑：XX |
| 1 | Refactor | — | ✅ 全绿 | 提取XX方法，消除重复 |

## 测试清单
| 编号 | 测试方法 | 覆盖的 SP/FP | 覆盖行为 | 优先级 |

## 关键实现说明
- [设计点：为什么这样做；并发/事务/异常等关键决策]

## 代码
[完整可编译文件清单，标注路径与新增/修改；测试文件与实现文件分开列出]

## 重构记录
| 手法 | 改动位置 | 改动前 → 改动后 | 理由 |

## 验证方式
[运行命令以当前栈 rules 的命令口径为准（定向测试与全量回归）；预期全部通过]

## 边界与风险
[已知边界条件、未覆盖场景、后续建议]
```

## 启动方式

输入 `/tdd` 并描述编码任务（实现某功能 / 修复某 Bug / 重构某模块）与涉及文件。收到后：① 读目标类及其依赖、上游设计文档，确认测试框架与既有测试风格；② 列本任务测试用例设计清单（含 happy path、边界、异常），请用户确认优先级与覆盖范围；③ 确认后按 Red-Green-Refactor 逐个推进，每轮输出循环记录；④ 全部完成后输出交付报告，落盘 implementation.md 并回写 tasks.md。多任务按 T 号顺序逐项交付，每项独立走完循环再进入下一项。
